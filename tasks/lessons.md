# Lessons

- When the user asks for a clean gameplay-cycle rewrite, do not stabilize the old loop with guard piles. Treat a desire to add a guard as a signal to identify and fix the broken contract or ownership boundary.
- Do not use `docs/WorldForge_runtime_problem_fixes_latency_memory_v5.md` as architecture or implementation guidance for this rebuild. It is historical diagnosis of old-runtime problems unless a specific idea is independently justified by the new clean pipeline.
- Before major gameplay-cycle architecture decisions, consult Oracle/GPT-5.5 Pro with a dry-run prompt and record the question, recommendation, accepted decision, and reason.
- Keep the scope to player message through player-facing narration/API response. Do not expand into world creation, character loading, or broad UI rewrite.
- If the main worktree is dirty with my own changes, commit or otherwise settle those changes in the normal branch before creating a new branch. Do not create a separate worktree to dodge my own uncommitted work unless the user explicitly asks for that workflow.
- Do not leave ad-hoc backend/dev-server processes running after a smoke test. Before starting a new backend on another port, stop the previous one; after the test, stop any listener I started unless I am about to use it again immediately.
- When using `Start-Process` for backend smoke tests, pass `PORT=<port>` through the process environment explicitly and kill listeners on both the intended port and the backend default `3001` during cleanup. A local `$port` variable does not set the child process port.
- A live `/api/chat/action` reaching `narrative` and `done` is not enough evidence for grounded narration. After any settled-packet/narrator change, compare the player-facing prose against the accepted tool result or Oracle result in logs/DB; otherwise the narrator can produce a plausible but different outcome.
- For failed-turn verification, do not stop at “SSE emitted error.” Also verify route-level restore succeeds and no `settled_turn_packets`, `narrator_attempts`, or `turn_sagas` rows were created; otherwise a hidden rollback failure can poison later playtests.
- When validating movement, first inspect the source campaign's actual `SceneFrame.movementCandidates` or location edge state. A failed move in an expired/archived scene fixture proves failed-route handling, not movement success/failure for the new turn cycle.
- For required local actor consequences, judge success at the actor-settlement contract level: at least one accepted runtime receipt satisfies the required visible reaction. Extra rejected actor tools after that receipt should be audit-only unless they are the only attempted receipt.
- For final acceptance clones, use source campaigns where the first player turn has not been made yet: prefer `chat_history.length === 0`, `settled_turn_packets === 0`, and no prior `/api/chat/action` evidence. Do not clone already-played smoke campaigns for the 3x60 acceptance lanes.
- In GM v1, do not use `inspect_known_fact` as a generic visible-object inspector. Visible/current/inventory objects should route through `find_object_candidates`; `inspect_known_fact` is for player-known facts/canon claims. If a bridge lookup misses, repair within lookup tools rather than adding a guard or narrating over the failed receipt.
- If a player action combines a physical state change with dialogue/procedure resolution, Stage 3 must split them into separate required backend steps. Do not let `record_dialogue_outcome` carry a player-applied mark, tag, annotation, inventory change, or other physical mutation without its own accepted state receipt.
- Stage 4 tool-request prompts must expose exact enum domains for semantic tools, not vague prose like "required when durable". For `record_dialogue_outcome`, map documentary/proof future use to `futureUseKind=evidence`, never `proof`, and omit optional strings instead of sending empty values.
- When v1 Stage 4 accepts a structural state-bearing tool before a terminal dialogue step, attach model-safe `state_receipt_N_M` aliases to that tool result and expose them in accepted context. Otherwise a later `record_dialogue_outcome` cannot correctly back `stateEffects.applied_now` and will either hallucinate malformed effects or fail schema validation.
- Stage 6 accepted evidence must summarize each accepted tool's actual result shape, not a generic observation shape. Bridge lookup tools such as `find_object_candidates` and `list_navigation_options` return `candidates`; if narrator evidence reads only older `legalTargets` / `legalMovement` fields, the packet is truthful but the player-facing narration loses the concrete options.
- Russian Stage 6 narration needs an explicit language contract, not only "Write in Russian." Proper nouns and accepted item/place labels may stay as written, but ordinary prose words, connectors, articles, transitions, and explanatory phrases must stay in Russian. Fix this at the narrator prompt contract boundary rather than post-processing text with word-replacement guards.
- Stage 4 tool input refs must never copy backend-only refs (`knowledge:*`, backend ids, UUIDs) from GM Read or context into runtime tool inputs. Contract prompts and tool hints must force visible labels/current aliases for `sourceRefs`, `subjectRefs`, `evidenceRefs`, and actor/entity/destination refs.
- Stage 4 language contracts must cover model-authored tool input fields too, not only final narration. Accepted `quote`, `summary`, `futureRelevance`, `claims[].summary`, and `stateEffects[].summary` can later feed narrator evidence, so they must use the turn language while preserving exact labels.
- When the user says to play manually for acceptance, do not replace that with an automated action generator. Transport helpers may only send a human-chosen action and collect evidence; they must not choose repeated gameplay actions or stand in for actual play decisions.
- Final acceptance lanes count only if they run cleanly from turn 0 to about 60 without failed, replayed, restored, or invalid player-facing turns. A lane with any contract failure or narration/state contradiction becomes diagnostic evidence only; start a fresh zero-turn clone after fixing the root cause.
- When checking whether an NPC is actually visible in a SceneFrame, inspect `current_scene_location_id`, not only broad `current_location_id`. Broad co-location can mean the NPC is in a sibling subscene and the GM is correct to ask clarification.
- Do not model inventory restowing of an already-held item as `transfer_item`. `transfer_item` is only for real custody, owner, location, or equip-state changes, and its `targetType` must be an actor/player/NPC/location category, never a container item.
- Russian narration/tool prose leaks can come from non-English scripts too. Language contracts must forbid unrelated scripts and mixed fragments, not only common English words, while preserving exact accepted labels and canon terms.
- Do not treat occasional model-script artifacts in otherwise grounded narration as gameplay-cycle blockers. Track them as prose quality unless they corrupt settled truth, state mutation, visibility, or playability; do not build deterministic language choke points for this goal.
- During gameplay-cycle proof, do not over-optimize prose quality or assume Russian is always the required narration language. Prose/language polish comes after the loop proves playable; current acceptance focuses on grounded state, valid tool receipts, pending cleanup, and coherent player-facing response.
- When the player addresses multiple already-visible NPCs, do not let GM Read/Stage 3 combine their labels into one `prose_role` or `create_scene_extra`. Pick one existing visible speaker as the dialogue owner and cite the other visible actors as evidence/source refs.
