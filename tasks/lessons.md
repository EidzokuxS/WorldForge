# Lessons

- When the user asks for a clean gameplay-cycle rewrite, do not stabilize the old loop with guard piles. Treat a desire to add a guard as a signal to identify and fix the broken contract or ownership boundary.
- For the clean gameplay-cycle rewrite, develop one primitive at a time: contract first, Oracle check for major design choices, isolated contract tests, integration with prior primitives, then real `/api/chat/action` manual evidence on zero-turn clones before moving to the next primitive.
- Treat the gameplay-cycle development unit as entrypoint-to-exitpoint: a zero-turn world plus one player message enters `/api/chat/action`, and the proof target is the frozen post-response world/API state that the next player input will see.
- For each gameplay-cycle primitive, verify both isolation and composition: first prove the primitive contract with focused tests, then wire it to the existing entrypoint-to-exitpoint path, then run about 10-15 one-at-a-time manual `/api/chat/action` turns on zero-turn clones after inspecting the actual post-turn state. Do not preselect future actions or count generated batches as evidence.
- For each primitive, explicitly name its required data, authoritative input, authoritative output, downstream consumer, failure behavior, and forbidden responsibilities before implementation. If those cannot be stated simply, the primitive boundary is not clean enough yet.
- Do not use `docs/WorldForge_runtime_problem_fixes_latency_memory_v5.md` as architecture or implementation guidance for this rebuild. It is historical diagnosis of old-runtime problems unless a specific idea is independently justified by the new clean pipeline.
- Before major gameplay-cycle architecture decisions, consult Oracle/GPT-5.5 Pro with a dry-run prompt and record the question, recommendation, accepted decision, and reason. If the browser UI says it is finalizing for several minutes, wait; do not assume the run is hung just because the answer is taking time.
- Keep the scope to player message through player-facing narration/API response. Do not expand into world creation, character loading, or broad UI rewrite.
- If the main worktree is dirty with my own changes, commit or otherwise settle those changes in the normal branch before creating a new branch. Do not create a separate worktree to dodge my own uncommitted work unless the user explicitly asks for that workflow.
- Do not leave ad-hoc backend/dev-server processes running after a smoke test. Before starting a new backend on another port, stop the previous one; after the test, stop any listener I started unless I am about to use it again immediately.
- When using `Start-Process` for backend smoke tests, pass `PORT=<port>` through the process environment explicitly and kill listeners on both the intended port and the backend default `3001` during cleanup. A local `$port` variable does not set the child process port.
- For clean runtime live proofs, prefer direct `Start-Process node --import tsx/esm src/index.ts` from `backend/` after setting `$env:PORT`, `$env:WORLDFORGE_GAMEPLAY_RUNTIME_CLEAN`, and `$env:WORLDFORGE_GAMEPLAY_CYCLE_V2` in the launcher shell. The first proof gate is SSE `done.runtime=gameplay-cycle-runtime`; a legacy-style event stream makes that clone diagnostic-only.
- A live `/api/chat/action` reaching `narrative` and `done` is not enough evidence for grounded narration. After any settled-packet/narrator change, compare the player-facing prose against the accepted tool result or Oracle result in logs/DB; otherwise the narrator can produce a plausible but different outcome.
- Treat a receipt-required player action that settles as a direct scene snapshot as diagnostic-invalid evidence. Inspect the GM Read and Judge typed admission path, add structured contract tests anchored in SceneFrame refs/capabilities, then retry from a fresh zero-turn clone.
- For failed-turn verification, do not stop at “SSE emitted error.” Also verify route-level restore succeeds and no `settled_turn_packets`, `narrator_attempts`, or `turn_sagas` rows were created; otherwise a hidden rollback failure can poison later playtests.
- When validating movement, first inspect the source campaign's actual `SceneFrame.movementCandidates` or location edge state. A failed move in an expired/archived scene fixture proves failed-route handling, not movement success/failure for the new turn cycle.
- For required local actor consequences, judge success at the actor-settlement contract level: at least one accepted runtime receipt satisfies the required visible reaction. Extra rejected actor tools after that receipt should be audit-only unless they are the only attempted receipt.
- For final acceptance clones, use source campaigns where the first player turn has not been made yet: prefer `chat_history.length === 0`, `settled_turn_packets === 0`, and no prior `/api/chat/action` evidence. Do not clone already-played smoke campaigns for the 3x60 acceptance lanes.
- In GM v1, do not use `inspect_known_fact` as a generic visible-object inspector. Visible/current/inventory objects should route through `find_object_candidates`; `inspect_known_fact` is for player-known facts/canon claims. If a bridge lookup misses, repair within lookup tools rather than adding a guard or narrating over the failed receipt.
- If a player action combines a physical state change with dialogue/procedure resolution, Stage 3 must split them into separate required backend steps. Do not let `record_dialogue_outcome` carry a player-applied mark, tag, annotation, inventory change, or other physical mutation without its own accepted state receipt.
- Stage 4 tool-request prompts must expose exact enum domains for semantic tools, not vague prose like "required when durable". For `record_dialogue_outcome`, map documentary/proof future use to `futureUseKind=evidence`, never `proof`, and omit optional strings instead of sending empty values.
- When v1 Stage 4 accepts a structural state-bearing tool before a terminal dialogue step, attach model-safe `state_receipt_N_M` aliases to that tool result and expose them in accepted context. Otherwise a later `record_dialogue_outcome` cannot correctly back `stateEffects.applied_now` and will either hallucinate malformed effects or fail schema validation.
- Stage 6 accepted evidence must summarize each accepted tool's actual result shape, not a generic observation shape. Bridge lookup tools such as `find_object_candidates` and `list_navigation_options` return `candidates`; if narrator evidence reads only older `legalTargets` / `legalMovement` fields, the packet is truthful but the player-facing narration loses the concrete options.
- Russian Stage 6 narration needs an explicit language contract, not only "Write in Russian." Proper nouns and accepted item/place labels may stay as written, but ordinary prose words, connectors, articles, transitions, and explanatory phrases must stay in Russian. Fix this at the narrator prompt contract boundary rather than post-processing text with word-replacement guards.
- Stage 4 tool input refs must never copy backend-only refs (`knowledge:*`, backend ids, UUIDs) from GM Read or context into runtime tool inputs. Contract prompts and tool hints must force visible labels/current aliases for `sourceRefs`, `subjectRefs`, `evidenceRefs`, and actor/entity/destination refs.
- Stage 4 language contracts must cover model-authored tool input fields too, not only final narration. Accepted `quote`, `summary`, `futureRelevance`, `claims[].summary`, and `stateEffects[].summary` can later feed narrator evidence, so they must use the turn language while preserving exact labels.
- When the user says to play manually for acceptance, do not replace that with an automated action generator. Transport helpers may only send a human-chosen action and collect evidence; they must not choose repeated gameplay actions or stand in for actual play decisions.
- Manual acceptance play must be turn-by-turn adaptive. Do not preselect a multi-turn action batch when later actions depend on unknown world/narration changes; after each turn, inspect the actual result, then choose the next player action from that current state.
- During manual acceptance, never choose concrete future actions from an assumed 5-7 turn plan. A forward plan may only be a loose intent or hypothesis; the next accepted player action must be selected from the actually observed post-turn world state.
- If the next action depends on how the world changes, stop at one live turn. Do not queue future player actions "for speed"; unknown state invalidates every concrete action after the first unresolved turn.
- Final acceptance lanes count only if they run cleanly from turn 0 to about 60 without failed, replayed, restored, or invalid player-facing turns. A lane with any contract failure or narration/state contradiction becomes diagnostic evidence only; start a fresh zero-turn clone after fixing the root cause.
- Intermediate 10-15 turn burn-ins are regression discovery only, not acceptance. The final gameplay-cycle acceptance still requires several different clean campaigns/clones at about 60 turns each with zero errors/restores/replays/invalid player-facing turns.
- A single clean 60-turn lane is still not final gameplay-cycle acceptance. Count final completion only after several different campaigns/clones each complete about 60 clean manual turns with zero failed, replayed, restored, or invalid player-facing turns.
- When reporting gameplay-cycle progress, treat "accepted" as a counter of clean 60-turn campaign lanes only. Primitive tests, one-turn live proofs, and 10-15 turn burn-ins can prove a layer or discover bugs, but they add 0% to final acceptance until the full multi-campaign 60-turn bar is met.
- At every gameplay-cycle progress report, separate diagnostic evidence from acceptance evidence. Do not imply percentage/acceptance progress from a primitive smoke test; only clean 60-turn lanes across multiple different campaigns move the final acceptance counter.
- When checking whether an NPC is actually visible in a SceneFrame, inspect `current_scene_location_id`, not only broad `current_location_id`. Broad co-location can mean the NPC is in a sibling subscene and the GM is correct to ask clarification.
- Do not model inventory restowing of an already-held item as `transfer_item`. `transfer_item` is only for real custody, owner, location, or equip-state changes, and its `targetType` must be an actor/player/NPC/location category, never a container item.
- Russian narration/tool prose leaks can come from non-English scripts too. Language contracts must forbid unrelated scripts and mixed fragments, not only common English words, while preserving exact accepted labels and canon terms.
- Do not treat occasional model-script artifacts in otherwise grounded narration as gameplay-cycle blockers. Track them as prose quality unless they corrupt settled truth, state mutation, visibility, or playability; do not build deterministic language choke points for this goal.
- During gameplay-cycle proof, do not over-optimize prose quality or assume Russian is always the required narration language. Prose/language polish comes after the loop proves playable; current acceptance focuses on grounded state, valid tool receipts, pending cleanup, and coherent player-facing response.
- When the player addresses multiple already-visible NPCs, do not let GM Read/Stage 3 combine their labels into one `prose_role` or `create_scene_extra`. Pick one existing visible speaker as the dialogue owner and cite the other visible actors as evidence/source refs.
- Manual playtest transport must reject non-array action input. In PowerShell, a single-item `@(...) | ConvertTo-Json` can become one JSON string; a runner that iterates it will send one character per turn and invalidate the lane. Validate `Array.isArray(actions)` before sending anything live.
- Manual `/api/chat/action` transport must send `campaignId`, `playerAction`, `intent`, and `method`; sending `message` or omitting `intent` only tests route schema failure, not gameplay runtime behavior.
- Do not run acceptance lanes on `node --watch`/`npm run dev`: a watcher restart during SSE produces `ECONNRESET` and invalidates an otherwise clean lane. For 0-60 acceptance, run a stable backend process (`node --import tsx/esm src/index.ts`) and restart it only between lanes.
- `check_route` is a lookup, not a mutation. A missing visible/legal route should settle as a negative observation (`routeStatus=not_visible_or_legal`) so the narrator can report the blocked route; it must not hard-fail and rollback the player turn.
- GM Read `situationSummary` and `actionInterpretation.intent` are classifier/intent text, not accepted world facts. Do not place them in settled-packet `visibleFacts` for mutating/tool-plan turns; only accepted tool, actor, oracle, or direct-resolution evidence may become narrator truth.
- A legal `check_route` receipt is still not movement. Stage 6 evidence and narrator prompt must say route availability only and forbid narrating travel/arrival/current-scene change unless an accepted `move_actor`/`move_to` receipt exists.
- Player route-feasibility checks for a concrete destination (`is/open/legal/safe/reachable route to X`, including Russian phrasing like `открыт ли маршрут к X`) are not ordinary NPC route claims. GM Read must route them through route/movement authority so Stage 3 can use `list_navigation_options`/`check_route`/`move_actor` or a grounded blocked-route outcome before narration makes the answer playable truth.
- `check_route` evidence must carry the current scene/location anchor and final narration must prefer that anchor over any origin named in raw player text. A route lookup from `East Exit Underground Passage` must never narrate that the player remains in `Shibuya Ward` just because the player action said "from Shibuya Ward".
- Empty successful lookup tools are still gameplay evidence. `inspect_known_fact` with no matches must narrate the checked non-confirmation/unknown result, not degrade into generic scene look-around or omit the player's requested check.
- GM Read `targetRefs`/`evidenceRefs` are not actor authority for narration. If the player action is first-person and no accepted actor/local consequence names an NPC, Stage 6 must narrate the player as the subject and must not turn an NPC ref into the actor performing the player's action.
- Do not let model-authored GM Read intent, sceneQuestion, targetRefs, or evidenceRefs trigger deterministic runtime hardening by themselves. Hardening at manual/raw-action boundaries must be anchored in the player's raw action plus the current SceneFrame/tool surface, or it can convert harmless local actions into unsupported tool plans.
- NPC presence/visibility is gameplay truth, not color. If the player asks who is visible/nearby, Stage 3 must include actor visibility authority (`list_visible_affordances` or `find_actor_candidates`), and Stage 6 must not narrate NPC presence from GM Read refs or guardrails alone.
- A visible NPC who cannot answer is still a speaker-owned dialogue outcome. `unavailable`/`no_current_answer` are only for no-visible-authority cases: omit `speakerRef`, set `authorityKind=no_visible_authority`, include `requestedRoleText`, and still provide quote or structured claims.
- Oracle can resolve uncertainty, pressure, notice, or resistance, but it is not a state mutation receipt. Explicit travel/return/exit/entry to a destination must settle through movement authority (`move_actor`/`move_to` or a grounded blocked route), and narration must not claim arrival from Oracle alone.
- If GM Read repair loops because a model changes `path` without the matching `turnGrounding`/`runtimeRequirement`, fix the ownership contract before validation. For explicit travel, normalize the read to movement `tool_plan` before repair instead of asking the model to rediscover the paired fields.
- Movement authority owns only route/travel/current-scene changes. If the player also watches a phone/device/item for a signal, message, call, instruction, alert, or status change during/after travel, Stage 3 must split a separate observation step and Stage 6 must not narrate appeared/absent status from `move_actor` alone.
- Live phone/device screen checks are active observations, not known-fact lookups. Route `device_signal_observation` / phone status tool needs to `start_search` (or a future dedicated device observation owner), never to `inspect_known_fact`.
- If one Stage 4 checklist step changes authoritative player-turn state, rebuild the model-facing SceneFrame and execution context before proposing dependent later steps. Local context ref updates alone are not enough; the next model prompt and bridge lookup snapshot must see the post-receipt world.
- Manual acceptance lane artifact names must be globally unique or pre-cleared before turn 1. The transport appends to an existing `output/phase95-manual-play/<lane>-manual.json`; if the printed turn index is not 1 on a fresh campaign, discard that lane as evidence and restart with a new clone/lane id.
- Narrator must not turn `start_search` `found=false` into observed absence. For phone/device checks, `found=false` means no confirmed discovery/receipt was created; it does not authorize "screen empty", "no signal", "stable signal bars", "no message", "no call", or "no instruction" narration.
- Narrator must not turn visual/object/person/route/document `start_search found=false` into observed absence either. `found=false` means no concrete discovery receipt was created; it does not authorize "not visible", "not present", "not found", "missing", "unavailable", or "none were present" claims without a separate accepted absence receipt.
- Scene-local positioning inside the current scene (standing by a column, waiting near a sign, taking cover, counting local landmarks) is not movement authority. It should use scene-local `log_event` or observation/search ownership; `move_actor` must not silently choose the only connected exit route.
- Narrator must not turn "phone/device held/ready/at hand" into screen/device status. Screen brightness, dark screen, signal bars, battery, messages, calls, notifications, and instructions require explicit accepted status evidence.
- `playerAction` is a request/framing input, not settled evidence. If a dialogue turn also includes local physical posture such as keeping distance, stepping back, gripping an already-held item, or not handing something over, Stage 3 must settle that posture with a scene-local receipt before narrator can state it as completed.
- Speaker-asserted street directions toward an unmodeled POI/micro-location are not movement authority. `move_actor` must not substitute a different legal connected route just because the named target is not modeled; first establish the target with local following/search/location/POI ownership.
- Oracle outcome tiers are not enough narrator evidence by themselves. The Oracle request must define pre-roll meanings for `strong_hit`, `weak_hit`, and `miss`, and the settled packet must expose the selected meaning; otherwise the narrator has to guess what the tier means and can invert or overextend the outcome.
- Oracle browser mode uses its own private Chrome profile at `C:\Users\robra\.oracle\browser-profile`. For ChatGPT login, open that Oracle profile with `--browser-manual-login --browser-keep-browser --browser-manual-login-profile-dir`, not normal Chrome or a random remote-debugging profile.
- Oracle-only weak hits are uncertainty evidence, not local navigation/search/POI receipts. Narrator must not describe walking progress, storefronts, signs, POI discovery/absence, or current-scene change from Oracle alone; materialize those facts with accepted `log_event`, search, candidate, reveal/create, route, or movement receipts.
- Do not count an Oracle browser run as "attached" from CLI status alone. If the user needs auditable context delivery, verify the ChatGPT UI shows an attachment or the saved transcript contains the full inline bundle; otherwise use a manual inline/rendered bundle fallback before relying on the answer.
- A short Oracle/ChatGPT smoke prompt is not a substitute for the required context bundle. If attachment upload fails, do not ask the architecture question without files/context; either retry with inline rendered file contents, verify the UI/transcript contains that bundle, or mark the Oracle attempt invalid and do not rely on the answer.
- When the user explicitly says to use the built-in browser, do not fall back to Oracle Chrome or prompt-only ChatGPT. Use the Browser Plugin path; if its Node-backed control surface fails before any browser action, report that exact blocker and stop the browser attempt rather than pretending context was delivered.
- For GPT/Oracle architecture review, a chat bubble that contains only the question is invalid evidence. Before relying on the answer, verify that the ChatGPT/browser UI actually received the relevant file bundle or inline `### File:` sections; otherwise treat the run as not attached and retry with real context.
- After a user correction about missing attachments/context, first perform the actual Browser Plugin action or record the concrete Browser Plugin blocker. Do not answer with intent-only compliance or use any GPT/Oracle answer unless the browser/UI transcript proves the context bundle was delivered.
- Oracle browser attachments can break the ChatGPT run before a conversation is created. If the user flags attachments as the cause, do not retry the same attachment path; switch to a smaller inline/rendered bundle (`### File:` sections) or postpone Oracle evidence, and never count a user-closed attachment-failed session as review.

- Do not call an Oracle browser smoke or review "attached" when it was run with `--browser-attachments never`; that is inline delivery. For attachment-required review evidence, use `--browser-bundle-files --browser-bundle-format text` and verify `meta.json` shows `browserBundleFiles=true`, `promptSubmitted=true`, a real transcript, and nontrivial usage before relying on it.
- Terminal dialogue receipts must contain the visible response content they authorize. For non-silence dialogue outcomes, require quoted speech or equivalent concrete response content at the tool-request schema boundary; otherwise narrator can only say that a response happened without knowing what was said.
- For v2 item custody/location transfers, dropping/giving/placing an equipped item may legitimately express `equip.mode=unequipped`; the backend-owned result is still `equipState=carried`, `equippedSlot=null`. Do not reject this as a schema error when the ownership mutation is otherwise valid.

Legacy `settled_turn_packets`, `turn_sagas`, and `narrator_attempts` may correctly remain empty for v2 slices; checking only legacy tables can falsely suggest packet persistence failed.
